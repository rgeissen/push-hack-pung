Push 3 Standalone · Schwung modules · Devices in Live

Move's modules, at home in Live on Push.

Pung runs the modules of Schwung, the module system of Ableton Move, on Push 3 Standalone. Every synth, audio effect and MIDI effect becomes a device in Live: you find it in Push's browser, play it with the pads, automate it and save it with your Set. On the Push screen, each module gets a view made for it.

01 · Vision

The idea

On Move, Schwung has to bring its own signal graph, because Move's firmware has none to offer: four tracks, one chain each. On Push, the best signal graph on the device is already there. It is Live.

So Pung does not build a graph. It makes every Schwung module a Live device and runs the module itself in a separate process, so a module can never take Live down. Live does what it does best: tracks, racks, parallel chains, sends, sidechains, automation, clip envelopes, MPE, latency compensation and saving with the Set. Pung does the two things only it can do: run Move's modules faithfully, and show them well.

The result is an instrument library that grew up on a small box with one encoder per parameter, now playable on Push's eight encoders, its pads and its large screen, inside a full Live Set.

02 · Vision

Principles

  • Nothing new to learn. Modules are found in Push's browser, loaded like any device, played with the pads and edited with the encoders. Pung's screen and web page are extras, never a door you have to go through.
  • A module can never take Live down. Modules run outside Live's process. Live waits at most half an audio block for a module; if the answer is late, that block is silent and Live carries on.
  • One instrument, two surfaces. A module's interface is cut into compartments. One compartment is one screen on the Push and one section of the web page, with the same names in the same order.
  • The default must be world class. Every module gets a designed view built from its own parameters, with no code from its author. A module draws its own screen only where that is substantially better and true to the instrument.
  • Open and licensed. Every module is built from its own source, ships with its licence texts and build notes, and has the complete source of its build published beside it.

03 · Implementation

Architecture

The device proxy

Live sees one VST3 plugin, Pung.vst3, whose factory lists one plugin class per installed module: Braids, OB-Xd, Dexed, CloudSeed and the rest. The plugin itself does no DSP. For every audio block it writes the block's MIDI, parameter changes, transport and input audio into shared memory, wakes the module's thread in Pung and waits for the output. It is the only Pung code inside Live, and it is small on purpose. The proxy is Push Hack's generic livedevice.so, which any hack can use.

The engine

Pung hosts each module instance with Schwung's own plugin API, the same contract the module has on Move. Each instance renders on its own realtime thread at Live's audio priority. Live renders tracks on several worker threads, so Pung devices render in parallel on all cores, where Move rendered everything on one. Module loads and the first warm-up render happen on a control thread before the instance is offered to Live, never on an audio thread.

MIDI effects

Live on Push has no slot for a MIDI-effect plugin from another maker: Live 13 scans a MIDI-in, MIDI-out VST3 as an audio effect. So a Pung MIDI effect reaches a sound in two ways. Every Pung instrument has a MIDI FX selector that loads the effect in front of the synth in the same chain. And each MIDI effect also exists as a device of its own ("Chord Track"), whose notes any other track takes with Live's MIDI From, Live's own instruments included. Measured on the device: 16 notes in, 48 out, all 48 heard by the instrument on the other track.

04 · Implementation

What Live gives a module

A Schwung module expects Move. On Push, every part of that contract is answered by Live, so a module runs unchanged.

The module expectsOn Push, from Live
128-frame blocksLive's block, rendered in Schwung's 128-frame blocks. Any Live buffer size works.
Tempo and beatLive's transport for each block: its tempo, its beat position and whether it plays. No sync settings to make.
MIDI inThe block's notes at their sample offsets. Pitch bend, mod wheel, sustain and pressure arrive as the MIDI bytes the module knows.
ParametersVST3 parameters with Schwung's names, units and value strings. A list is a list parameter, an integer is stepped. Bank N on Push is the module's own bank N.
Module stateThe plugin's state, saved with the Live Set, undo included.
Audio inputAn audio effect's input is the audio of its place in Live's chain, so it works on any track, return or rack chain.
Browser entriesA rack per module in the User Library, with its parameter map and Live's own browser tags (Devices › Synthesizer › FM, Devices › Reverb, and so on).

05 · Implementation

The Pung view

Push's own device view already edits every Pung device. The Pung view goes further. When you select a Pung device and Push shows its device view, push-manager hands the screen and the encoders to Pung, and Pung draws the device in its own way. Its controls are Push's own, measured on a Push: the devices on the upper buttons, the selected one's button opens it, its pages on the lower buttons, the jog wheel steps through them, and Mute or Delete with a device's button act on it. Device View shows Push's view of the same device, and pressed again brings Pung's back. The pads, transport and editing buttons stay with Live throughout.

Three levels of interface exist on the Push, each further from Push's own look: Push native (always there), Pung default (designed from the module's parameters, for every module) and Pung custom (a module's own screens, where they earn their place). The design principles describe them in detail.

Moving between devices is measured, not hoped for. A frame never mixes two devices. A knob writes only to the device on the screen, once Live has confirmed it. A device you have seen before is drawn at once, and Pung's first frame typically comes about 50 ms after it gets the surface.

Pictures that play

The default view recognises four structures in any module's parameters, by their names and by sitting side by side: an envelope, a filter, an LFO and a mix of sources. It draws each one over the encoders that set it. While the device plays, the pictures show what the sound is doing:

  • every note is a dot running along the envelope in time, and a bar under it lights the stage each note is in, on every module the same way;
  • the real spectrum sits behind the filter's curve;
  • an LFO's dot moves where its phase can be known.

The rule is strict: nothing moves unless the sound moves. The motion is timed by what Pung knows: the notes, Live's beat, the times a module states, the sound itself. Where a module gives its times no unit, Pung reads them from the knob and lets the sound correct it. Where an instrument can tell its own state, Pung shows it: Mini-JV's envelopes run in the JV-880's own time, measured off the emulated instrument, Dexed's in the DX7 engine's own, and Mini-JV's display shows every one of its 28 voices' level and filter.

One live session per sound feeds both the Push and the web page, so the two always agree. It runs at 30 frames a second while someone watches, and stops when nobody does.

06 · Implementation

Builds and licences

Move's modules are built for ARM; Push 3 is x86-64. Every module is built again from its own source. The recipe is read from the module's own build script, never run: only the compiler touches the source. Each build is checked as an x86-64 ELF against the Push's glibc 2.35, with its entry point, and the Push runs a real load test at install.

  • A module is published only when its licence is known: a licence file, its module.json, its README, or a recorded permission.
  • Every package carries its licence texts and build notes. The complete source of every build is published beside it, as GPL-3.0 section 6(d) asks.
  • Firmware and ROMs are never in a package. Modules that need them (JE-8086, Mini-JV, Osirus) take the file you add yourself, recognised by its checksum.
  • A Pung release is one file with the whole catalog inside. The Modules page installs from that copy on the Push's own disk: nothing is downloaded at install.

07 · Implementation

Module pipeline

Schwung's catalogue grows every week. Pung keeps up with it through an automatic conversion and serving pipeline, which is already built and running: a small service that does, unattended, what the previous section describes by hand.

  • Watch. Every night it reads Schwung's catalogue and every module's latest release, and sorts each module into new, updated, current, built, failed or withheld (no known licence, or no published source).
  • Convert. New modules and new releases are built for the Push's x86-64 from their source at the release tag, checked, and packaged with their licence texts, build notes and complete source, into a staging catalog. Builds run at the lowest priority with two compiles at once, so the machine they share keeps its other work.
  • Review and serve. Nothing reaches users on its own: a maintainer reviews the staging catalog and publishes it, and can put the previous catalog back. Pung's Modules page reads a served catalog as readily as the one inside its release.

During the test phase, modules ship inside each Pung release: one file, nothing to host, and every tester on the same set. When the test phase is over, the plan is to switch on the served catalog, so new modules and module updates reach every Push as Schwung publishes them, without waiting for a Pung release.

08 · Push Hack

Push Hack core extensions

Pung is a hack for Push Hack, the framework that opens Push 3 to community software. Pung keeps its weight in its own repository: the engine, the Pung view, the module builds, the catalog and the pipeline all live there. What Pung asks of Push Hack is deliberately small, and shaped so that other hacks gain from it as much as Pung does.

  • Opt-in throughout. Each addition changes nothing until a hack declares it in its hack.json or asks for it through the client library; push-manager only watches, read-only, for the moment one does. A Push Hack install with no such hack behaves exactly as before.
  • Self-contained. The largest piece, the Live device layer, is a new package that nothing existing depends on: about 1,100 lines of Go and 1,100 of C++ for the plugin, which ships prebuilt. If the maintainers prefer to keep the core small, it can live as a module of its own beside the core, and Pung will take it from there.
  • General, not Pung-shaped. Every part is written for any hack, comes with its tests, and is documented in Push Hack's own docs, with a small example hack for the device layer.
  • Small, independent steps. The changes can land as separate pull requests, each reviewable and useful on its own: the MIDI reader fix, the client fields, pad pass-through, the device layer, then the device-view stand-in.

Status

These extensions are part of Push Hack: pull request #102 landed in Push Hack 0.2.0-alpha, and hacks get the device layer with core/v0.6.0, which Pung builds on. Merged since: pull request #106 makes the rack writer and the uninstaller remove only the racks a hack wrote itself, so the device presets you save with Push stay, and pull request #108 gives Live its pad lights back every time an app hands the surface over. Pung is listed in Push Hack Catalog (pull request #109). Proposed next: push-manager shows an app's first frame instead of blanking the screen while it hands over (about 100 ms of black today).

09 · Implementation

Rules from measurements

Measured on a Push 3 with Live 13 beta. Each one shaped the design.

  • Live scans plugins only when it starts. A new module is a new plugin class, so installing modules ends with one Live restart (Apply on the Modules page, about 30 seconds; the Set is recovered).
  • Push names plugin banks "Bank 1", "Bank 2". Every Pung bank is padded to whole pages, so Push's Bank N is the module's own bank N.
  • List each parameter once. Live keeps a value per listed entry; a parameter listed twice shows a stale value in one place.
  • Defaults are real. Live sends a device its default values when it loads it, so a default must be the engine's true starting value, or a synth loads at volume 0.
  • Never remove a plugin a Set has used before Live restarts after a crash: Live replays the Set's history while recovering, and a missing plugin crashes it.
  • The Pung view's drawing budget is 8 ms a frame, 14 ms for a full-screen takeover. JE-8086's Patch screen draws in 3 to 5 ms on the device. A page of plain knobs draws in about 7.4 ms; the live spectrum adds about 1 ms, and a moving dot nothing measurable.
  • Match Live's parameters by position, not by name. A JV-880's four tones share their parameter names. Matched by name, 97 of Live's parameters belonged to several keys at once, and a knob on one tone could change another. Pung now matches each parameter by its place in the device's list, and checks the name.
  • A module applies a patch in its own time. Mini-JV boots its ROM and loads patches through its emulated firmware, later than any fixed delay. So every device is read back every 3 seconds, and Live hears whatever changed.
  • Most modules cannot say how long their envelopes take. Of 307 envelope time knobs across 100 modules, 54 state a unit and 95 have a range in seconds; the rest have none. So the dots run on the knob where they must, and the sound itself corrects the volume envelope's.

10 · Status

Status and next steps

Pung 0.1.16 is the current release. It brings 102 modules and the Pung view, with custom screens for JE-8086, Mini-JV, Dexed and Osirus. The default view draws envelopes, filters, LFOs and mixers for any module, and they play live as the sound moves, on the Push and on the web page; every envelope is one picture, each note a dot on its own clock, in the instrument's own times where Pung can know them; and the view's buttons, jog wheel and lights work as Push's own device view does. There is one sound browser for every module, built on Schwung's user presets, so sounds move between Move and Push. Also included: the web page, the Modules page and Live browser tags for every module. It is a testing release: expect rough edges, and tell us about them.

  • Overtake modules, which take over Move's whole surface, need a Move compatibility runtime and do not run yet.
  • Modules render at 44.1 kHz. At another Live sample rate, pitch and tempo are off.
  • Next on the Push screen: more instruments telling their own live state, as Mini-JV does, and custom screens for the instruments that deserve them (Braids and OB-Xd first).
  • After the test phase: the served catalog from the module pipeline, so modules update as Schwung publishes them.
  • Next for installing: browsing and installing modules from the Push itself.

Read the manual to install and use Pung, and the design principles to bring a module to it.
